# M0 spike notes

## Spike 1: panel level, Spaces, fullscreen, transparent hit testing

Date: 2026-11-21. macOS 26.6.2, Swift 6.4.2, built-in display 1470x956 with a 179x32 notch.

### Level, Spaces and fullscreen (level `.statusBar`, collection behavior `[.canJoinAllSpaces, .stationary, .fullScreenAuxiliary, .ignoresCycle]`)

| Check | Result | Evidence |
|---|---|---|
| Pill visible on Space 1 | yes | screenshots |
| Pill visible on another (empty) Space | yes | user screenshot |
| Pill stays still while swiping between Spaces | not checked | the user did not test the swipe itself |
| Fullscreen Safari, menu bar hidden | yes, pill sits in the black notch band | user screenshot |
| Fullscreen Safari, menu bar slid down | yes, pill stays visible and flush with the notch | user screenshot |
| Fullscreen Terminal | not checked separately | Safari passed with the same level |
| Mission Control (F3) | no tile, no glitch | user report |

`islandLevel = .statusBar`. No higher level was needed, so `mainMenu3`, `popUpMenu` and `screenSaver` were not tried.
The flush idle pill sits over the physical notch, where the display has no pixels, so it is not visible to the eye (screenshots capture it, the screen does not show it). This is the wanted "invisible when idle" behavior.

### Transparent pixels (300x60 test panel: left half alpha 0, right half alpha 0.01)

Synthetic mouse events (CGEvent) were posted over each half and the panel's log was counted.

| Check | Result |
|---|---|
| Hover over the alpha 0 half | `enter`/`moved` received (6 moves at x<150) |
| Hover over the alpha 0.01 half | `moved` received (6 moves at x>=150) |
| Click on the alpha 0 half | **passed through**, no `mouseDown` on the panel |
| Click on the alpha 0.01 half | received (`mouseDown x=225`) |
| Visibility of 0.01 | not needed |

`hitOpacity = 0`. A fully transparent hot zone and hover margin receive tracking events, and clicks fall through to what is underneath (this is what criterion 7 wants). Clicks were tested once per half; Task 9 rechecks that the margin does not swallow menu bar clicks.

## Spike 2: one-time frame grow during a spring animation

Date: 2026-11-21. Same machine as Spike 1.

Setup: a notch-sized panel with a tracking area. On `mouseEntered` the frame grows once to 764x338 (instantly), then a SwiftUI spring (response 0.35, damping 0.8) expands a red shape inside it. On `mouseExited` the shape collapses and, in the `completionCriteria: .removed` completion, the frame shrinks back (only if the shape is still collapsed).

Synthetic hovers (CGEvent) drove 40 enter/leave cycles: 10 full, 10 leaving 120 ms into the expand, 10 more with a re-enter 150 ms into the collapse, plus the re-enter cycles.

| Measure | Result |
|---|---|
| Collapse callbacks per collapse | exactly one (40 for 40) |
| Callbacks that arrived after a re-expand started | 10, all with the shape already expanded again. The guard correctly left the panel big. **Task 7/8 must ignore a stale collapse completion** (review focus 3) |
| `mouseEntered` events | 70 for 40 real entries. Resizing the panel rebuilds the tracking area while the pointer is inside, so macOS re-sends `mouseEntered`. **A repeated "inside" must be a no-op** (review focus 2), and Task 9 re-samples the pointer after each resize |
| Visible flicker, size jump or faint box around the collapsed panel | **none seen** by the user, who watched the whole run |

Limits of this check: it was eyes-only. No screen recording was possible (this terminal has no Screen Recording permission and the installed `ffmpeg` is broken), so single-frame glitches that the eye cannot catch were not measured. The cheap variants (`display: false` + layout, zero-duration animation group) were not needed.

**`frameStrategy = growOnce`.** The two-panel fallback is not needed. Re-evaluate in Task 13 if flicker shows up in real use.

## Launch at login (Task 11 fallback)

Date: 2026-11-22. Launch at login moved to M1 (ad-hoc signing).

Observed: the real status menu showed `Launch at login (unavailable)`, which is `SMAppService.mainApp` status `.notFound`. Shima was absent from System Settings > Login Items. No register error was logged because the item was disabled.

Cause NOT isolated. Candidates: ad-hoc signing and/or the bundle living in `dist/` instead of `/Applications`.

Decision: the menu item and `Sources/Shima/LoginItem.swift` are removed from M0. `LoginItemMenu` and its tests stay. M1 retries after the stable self-signed certificate exists and with the app copied to `/Applications` (needs the user's OK, since it is outside the repo).
