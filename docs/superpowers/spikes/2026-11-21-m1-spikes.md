# M1 spike notes

## Spike 1: PlaybackStateChanged

Date 2026-11-22. Spotify 1.3.10.2586, macOS 26.6.2. Private session, volume 0, driven by hand; no commands were sent to Spotify. Log lines were not marked per step (the marker file writes were overwritten by the observer), so seek and next/previous are inferred from timestamps and position jumps. No ad played. Track titles and artists are not recorded here.

| Item | Result |
|---|---|
| Notification | `com.spotify.client.PlaybackStateChanged`, `object` = `com.spotify.client` |
| Keys while playing or paused | `Album` (String), `Album Artist` (String), `Artist` (String), `Disc Number` (Number), `Duration` (Number), `Has Artwork` (Bool), `Name` (String), `Play Count` (Number), `Playback Position` (Number), `Player State` (String), `Track ID` (String), `Track Number` (Number) |
| Keys on a pause/play within the same track | Only `Duration`, `Playback Position`, `Player State`, `Track ID` (no `Name`, `Artist`, `Album`) |
| Keys when `Player State` is `Stopped` | Only `Player State` |
| Units | `Duration` is milliseconds (187146 for a 3:07 track); `Playback Position` is seconds as a fractional number (119.158) |
| `Player State` values seen | `Playing`, `Paused`, `Stopped` |
| `Track ID` form | `spotify:track:<22 chars>` |
| Artwork URL | Not in the payload. `Has Artwork` is only a Bool. The URL needs an Apple Event (Spike 2) |
| `payloadComplete` | **false** in the plan's sense: `Name` and `Artist` are present on a track change and on launch, but a pause/play of the same track carries only state, position, duration and track id. The reducer must keep the earlier name and artist |
| `ratePlaying` | **0 per minute**: over 62 s of untouched playback the only broadcast was the automatic track change. No periodic ticks |
| `seekPosts` | Probably yes: a jump of position from about 41 s to 142 s arrived as a `Paused` then a `Playing` broadcast about 1.2 s apart. Not proven (steps were not marked) |
| Volume change | No broadcast seen |
| Next track | One broadcast, new `Track ID`, `Playback Position` 0, `Player State` Playing |
| Auto-advance | One broadcast, same shape as next track |
| Launch order | `didLaunch` (pid) first, then a `Stopped` broadcast about 0.12 s later, then a full `Paused` broadcast about 0.28 s after that (the restored track) |
| Quit order | A `Stopped` broadcast about 0.17 s **before** `didTerminate`; nothing after `didTerminate` |

### Decisions
- `payloadComplete`: a track change or launch carries everything except the artwork URL; a same-track pause/play does not carry name and artist. Task 7 parses what is present and leaves missing fields `nil`; Task 8's reducer keeps the previous name and artist when the track id is unchanged (already its rule). Task 9 refreshes through Apple Events once per new track id for the artwork URL, and on a broadcast that has no display fields (`!hasDisplayFields`).
- `ratePlaying` 0 per minute (below 6): no position-only skip rule needed.
- `seekPosts`: no code change; the position re-syncs on island open (design 8.2). Criterion 5 should confirm a seek on the real island.
- Units match the Task 7 test dictionary (`Duration` ms, `Playback Position` s): no change.
- `Stopped` arrives before `didTerminate`, not after: the not-running rule in Task 8 still protects against a late reading but is not exercised by quit; no change. `didLaunch` comes before the first broadcast: no change to Task 17.

## Spike 2: raw Apple Events by pid

Date 2026-11-22. Signed with the existing Apple Development identity via `SHIMA_SIGN_ID`; designated requirement has `identifier "local.shima"` and the certificate leaf, no `cdhash`. Titles and artists are not recorded.

| Item | Result |
|---|---|
| `pPlS` | enum (`enum`); playing `kPSP`, paused `kPSp` (stopped expected `kPSS`, not observed) |
| `pPos` | `doub`, seconds, fractional (211.686) |
| `pnam`, `pArt`, `pAlb` of `pTrk` | `utxt` |
| `pDur` of `pTrk` | `long`, **milliseconds** (302147) |
| `aUrl` of `pTrk` | `utxt`, 64 chars, begins `https://i.scdn` (https already) |
| `ID  ` of `pTrk` | `utxt`, 36 chars, `spotify:track:<22 chars>`: same form as the broadcast |
| `pALL` of `pTrk` | **error -10000**: not usable |
| Timing | each read about 16 ms warm; the first read after launch timed out at 2004 ms (`-1712`) while the Automation prompt was up, then every read succeeded after Allow |
| Commands | `spfy`/`PlPs` toggled playing to paused and back; `Next` moved to a new track (duration changed, position reset) and started playing; `Prev` restarted the track (Spotify restarts when past about 3 s) |
| Dead pid | `deadPidCode = -600` for an exited `/usr/bin/true` and for the pid of a quit Spotify; Spotify never launched (`pgrep -x Spotify` empty each time) |
| Grant | survived a rebuild with the same identity: no second prompt (`grantSurvivesRebuild = yes`) |

### Decisions
- `snapshotStrategy = perProperty`: `pALL` fails, so Task 16 sends 8 events per snapshot (`pPlS`, `pPos`, `pnam`, `pArt`, `pAlb`, `pDur`, `aUrl`, `ID  `, the last six of `pTrk`). Reads are about 16 ms each, so a snapshot is about 130 ms on the private queue; coalescing in `SpotifyRequestGate` already protects against bursts.
- `durationUnit` ms, `positionUnit` s: matches the Task 7 test dictionary and Task 16's expected conversion.
- `scriptTrackIDForm` equals `trackIDForm`: no `normalizedTrackID` needed.
- `artworkURLForm` is `https://`: no `http` upgrade rule needed.
- Deadly checks passed: no relaunch, `-600`, grant survives rebuild. No stop condition hit.
- Task 16 must treat the first read after the Automation prompt may take up to the 2 s timeout and return `-1712`; the existing error mapping (`-1712` timeout) covers it, and the next broadcast or open refreshes.

## Spike 3: live-frame change during hover

Method: throwaway glue per plan Step 2 (real HoverMachine + `idleGeometryChanged` rule), SHIMA_DEBUG=1 ad-hoc build, real pointer driven by scripts/drive.swift, logs in .build/s3-<case>.log (harness: scratchpad/cases.sh, reset = `fake paused; move 735 400; sleep 2500` before each case; 1500 ms reset was too short when the previous case ended expanded and contaminated logs).

| Case | frame lines | hover lines | Result |
|---|---|---|---|
| 1 idle toggles x5 | 10 (w=245/179 alternating) | 0 | PASS |
| 2 open, toggle | 2 (expanded x1, idle w=245 after collapsing->collapsed) | 5 | PASS (none at toggle) |
| 3 dwelling (dwell 1500) | 4: idle 245, idle 179, expanded, idle 179 | collapsed->dwelling, dwelling->expanded, ->leaving, ->collapsing, ->collapsed | PASS (stays dwelling through both toggles) |
| 4 pointer on wing, live off (dwell 1500) | 2 (idle 245, idle 179) | collapsed->dwelling, dwelling->collapsed | PASS (no expanded) |
| 5 live on next to notch | 2 (idle 245, expanded live=true) | collapsed->dwelling->expanded | PASS after glue fix (see below); FAIL as written in plan |
| 6 mid-expand | 2 (expanded live=false at start, idle 245 after collapse) | 5 | PASS |
| 7 mid-collapse re-entry | 3 (idle 245 at fake playing, expanded, idle 179 final) | collapsing->dwelling->expanded x2, one final collapse | PASS (no frame on re-entry) |
| 8 rapid toggles x10 | 20, last w=179 live=false | 0 | PASS |
| 9 wiggle while live | 3 (idle 245, expanded, idle 245 final) | expanded<->leaving x~40, exactly one `-> collapsing` | PASS |

No repeated hover transitions without a pointer step in any case.

### Plan glue bug found (case 5)
As written, `.shrinkPanel` (turning live on) calls `setFrame(idle(live:true))`, whose `refreshHotRect()` reads `state.live` while it is still false, so the hot rect is the 179-wide idle rect inside the 245-wide panel. A pointer already on the new wing (x=630) never produces mouseEntered, and later 1pt moves do not either (log: one frame line, zero hover lines, 3 reruns + a jiggle). Fix: refresh the hot rect after `state.live = true` (or pass the target `live` into the hot rect computation). Task 12 must compute the idle hot rect from the TARGET live state, not the applied wing state. With the fix case 5 passes (collapsed->dwelling->expanded 107 ms after the frame).

### HUMAN glance
User watched cases 1 and 2 (five wing toggles, then one open and toggle) on the real screen: "all smooth, no flicker".

### Decision
liveFrameStrategy = growThenAnimate (all 9 cases pass in logs; no flicker per the human glance; if it flicks on live start only, try variantA/variantB per the rules). Task 12 implements the throwaway rule `(_, .idleGeometryChanged) -> panelLarge ? [] : [.shrinkPanel]` plus the hot-rect-from-target-live fix.

## Spike 4: clicks on the non-key panel

Setup: TextEdit frontmost (activated, clicked into its window at 300,400); drive.swift with real pointer events; Spotify not running. Panel is 396 wide (island 360 centred, 18pt inset), so island-local (215,112) = global (786.5,128). Throwaway: 32x32 white circle (Button .plain, or Circle+.onTapGesture with SHIMA_SPIKE_TAP=gesture) and an unhandled 88x88 grey "artwork" rect at island-local (14,44) (artwork click at 600,60 hits it).

| variant | taps for 2 clicks | active/key/main | taps for artwork click | `app became active` | frontmost before == after |
|---|---|---|---|---|---|
| button, FIRSTMOUSE=1 | 2 | false/false/false (both) | 0 | 0 | TextEdit == TextEdit |
| button, FIRSTMOUSE=0 | 2 | false/false/false (both) | 0 | 0 | TextEdit == TextEdit |
| gesture, FIRSTMOUSE=1 | 2 | false/false/false (both) | 0 | 0 | TextEdit == TextEdit |

Log excerpt (button, FM=1): `spike tap active=false key=false main=false` x2 (~620ms apart), no `app became active`.

Decision: clickStrategy = buttonFirstMouse (first variant in rule order passes all criteria).

FIRSTMOUSE=0: contrary to expectation, the first click was NOT swallowed (2 taps for 2 clicks). The panel never becomes key (canBecomeKey false, nonactivating), so there is no "first click only activates/keys the window" step to swallow; acceptsFirstMouse is apparently not consulted. Keep acceptsFirstMouse=true anyway as harmless insurance (e.g. if the app ever becomes active), but it is not load-bearing. The gesture variant also works, so either is fine.

Step 3 (human cursor/press glance) left to controller.

### HUMAN glance
User hovered the island and moved over the white circle: the cursor stays the normal arrow; on press the circle dims to grey while the button is held (the plain button style's pressed state), no system bezel or flash.
